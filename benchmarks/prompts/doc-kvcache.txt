注意力机制与 KV Cache 的由来
本文解释 KV Cache 是什么、为什么存在，以及它的规模由哪些因素决定。
方案对比见 02-schemes.md，具体计算见 03-sizing.md。
1. QKV：一次检索过程
注意力机制中，每个 token 都会被投影成三个向量：
计算流程：用 Q 与所有 token 的 K 比对得出匹配度（注意力分数），再按匹配度加权汇总
各 token 的 V，得到输出。
以「小明把书放在桌上，因为它很重」为例，处理「它」时，它的 Q 表达「我在指代哪个
实体」，与「书」的 K 匹配度最高，于是「书」的 V 被大量吸收进「它」的表示中，模型
由此确定「它 = 书」。
三者的来源：token 的表示分别乘以 W_Q、W_K、W_V 三个权重矩阵，这些矩阵是训练学出来的。
为什么只缓存 K 和 V
自回归生成时，第 N 个 token 的 Q 需要与前面所有 token 的 K 比对，并汇总它们的 V：
前面所有 token 的 K、V → 反复被读取，必须保留
当前 token 自己的 Q → 用完即弃，后续 token 有各自的 Q
不缓存则每生成一个 token 都要把历史 K、V 全部重算，计算量随长度爆炸。缓存是以显存
换算力的交易，代价是显存被 KV 占据，上下文越长占用越多——这正是卸载需求的源头。
2. 复杂度：存储线性，计算平方
一个常见误解是 KV Cache 占用为 O(N²)。实际上：
O(N²) 的中间产物是注意力分数矩阵，计算完即丢弃，不进缓存。
用图论类比：N² 是「边」的数量（token 两两之间的关系），O(N) 是「点」的数量。
缓存存的是点，不是边。
3. 多头注意力与 KV 头数
模型并行运行多组注意力，每组称为一个「头」，各自关注不同的语义侧面。
以 Qwen2.5-7B 为例（num_attention_heads: 28、num_key_value_heads: 4）：
*num_key_value_heads 的含义：每个 token 在每一层需要存储几组 K/V 向量。
每组包含一个 K 向量和一个 V 向量，维度均为 head_dim。
具体到一个 token 在一层中：
多组的意义在于各组关注不同侧面——例如一组编码指代信息、一组编码语法角色、
一组编码语义类别。只存一组则视角单一，模型能力下降。
Q 头数不影响缓存（Q 用完即弃），只有 KV 头数直接决定显存占用。GQA 的全部价值
质量损失有限的原因：各 Q 头的提问角度依然彼此不同，只是共享同一批索引；组内的
若干问题本就语义相近，共用索引损失不大。
4. 层数：宽度与深度是两个轴
一个 token 在每一层都是 hidden_size 维（Qwen 为 3584），宽度全程不变，变的是
数值——每层重新加工一次。
宽度（维度）= 每一步能携带多少信息
深度（层数）= 能串联多少步推理
注意力头是把 hidden_size 切分成若干份（28 × 128 = 3584），并非额外增加宽度。
单层注意力只能完成一次信息汇聚。多跳推理必须分层完成，因为后一步的查询依赖
各层存在稳定分工（可解释性研究的普遍结论）：
每层的 K/V 各不相同
各层有独立的 W_K、W_V 权重，且输入也不同（第 N 层的输入是第 N-1 层的输出，
已融合上下文）。因此同一个 token 在不同层的 K/V 编码的是不同抽象层次的信息：
生成下一个 token 需要从第 1 层重新走完整前向传播，每层的注意力都要查询该层
自己的缓存。注意力不跨层，层间只通过「输出→输入」传递。
因此 28 层就是 28 套互相独立、不可替代的缓存：
KV Cache 存的不是「一份数据的 28 个副本」，而是「28 个不同抽象层次的理解快照」。
代码实现上各层是同一个类的多个实例（ModuleList 循环调用），代码相同但权重不同
——同一条产线，每个工位装了不同的刀具。
5. 与「思考深度」无关
推理模型的 thinking budget / reasoning effort 是横向延长序列（生成更多思考
token），与纵向的层数无关。层数在训练时定死，推理时无法调整。
确有 early-exit、层跳过、Mixture-of-Depths 等动态调整层数的研究方向，
但尚未进入主流推理框架，vLLM / SGLang 目前均为固定层数。
但思考模式会显著放大 KV 占用——思考 token 与普通 token 在注意力机制中毫无区别，
*思考内容能否跨请求复用前缀，取决于它是否保留在对话历史中，两种情况都很常见：
被剥离 → 不可复用：DeepSeek-R1、Qwen3 等模型的官方建议是多轮对话时不要把
上一轮的 reasoning_content 放回历史（对后续轮次无价值，且浪费上下文窗口）。
此时思考 token 生成后即废弃，进不了可复用前缀。
被保留 → 高度可复用：Agent 的工具调用循环中，每次工具调用都是独立请求，
而上下文（含此前的思考内容）持续累积。这是前缀缓存收益最大的场景之一。
*对卸载而言，思考模式的主要压力在生成期间的活跃显存占用，而非缓存复用。
单个开启思考的请求在生成过程中需持续持有数百 MiB 的 KV 且只增不减，并发几路即可
占满显存。这与长文档场景的「一次性 prefill 大量 KV、之后大量复用」是两种不同的
负载模式，卸载策略也应有所区别——详见 04-serving.md。

2. MHA / MQA / GQA：调整保留几组 K/V
三者在同一条轴上，MQA 与 MHA 是 GQA 的两个极端：
*GQA 是当前的事实标准。 实际取值差异很大：
共用越多越省显存。质量损失有限的原因见 01-attention.md 第 3 节。
3. MLA：不减头数，改为低秩压缩
*MLA 不在上面那条轴上。 它不减少头数，而是把 K、V 联合压缩成一个低秩潜在
向量存储，使用时再上投影还原。
DeepSeek-V2-Lite 的实际参数：
不乘 2：K 与 V 被压缩进同一个潜在向量，一份数据同时还原两者
不乘头数：该潜在向量为所有头共享
额外的 + qk_rope_head_dim：RoPE 位置编码无法作用于压缩表示，故 key 被拆成
两部分——128 维走压缩路径，64 维单独保留并施加 RoPE（称为解耦 RoPE），
这 64 维同样全头共享
压缩效果：若按 GQA 方式存储，每层每 token 需 16 × (192 + 128) = 5,120 个元素；
MLA 实际只存 512 + 64 = 576 个，压缩约 8.9 倍。
存储量低于 MQA，质量接近 MHA，代价是计算更复杂、对推理框架的支持要求更高。
4. SWA 是另一条正交的轴
*SWA（Sliding Window Attention，滑动窗口注意力）常与上面几个并列出现，
但它回答的是完全不同的问题：
*两者正交，可以叠加。 GPT-OSS-20B 即为典型：其 num_key_value_heads: 8 是标准
GQA，同时 24 层中有 12 层使用窗口为 128 的滑动窗口。准确描述是「GQA + SWA」，
而非第五种独立方案。（benchmarks/kv_size.py 输出中的 SWA 标签是简写，
指「含滑窗层的模型」。）
滑窗层只保留最近 N 个 token 的 KV，超出部分直接丢弃，因此其占用不随上下文增长，
在长上下文场景下极为省显存——代价是这些层无法直接看到远处的信息，需依赖全注意力
层与层间传递来弥补，故实践中多为二者交替排列。

本节信息检索于 2026 年 8 月，该领域迭代很快，引用前建议复核。
*主流开源模型的绝大多数仍是 GQA（Llama-3、Mistral、Qwen2.5、GLM-4 这一代），
它是效率与质量的最优折中。但 2026 年榜单前列的模型基本都已走出纯 GQA：

而新一代 GLM-5.2 已改用 MLA。

第四条轴：线性注意力混合
Qwen3.5、Kimi Linear、MiniMax-01 采用混合架构：大部分层用线性注意力

推理系统侧的 KV Cache 管理
前三篇讲的是模型架构决定 KV 有多大，本文讲推理系统如何存放、复用和搬运这些
KV——也就是卸载工作的实际战场。
文中带具体数字的推算均标注了假设条件，未经实测的部分列在文末「待验证」中。
1. Prefill 与 Decode：两种截然不同的负载
同一套权重、同一套代码，但数据形状差异巨大，导致两个阶段的瓶颈完全不同。
Decode 的单步流程
Decode 是带宽瓶颈
以 Qwen2.5-7B-AWQ、32K 上下文、RTX 4080 估算，生成一个 token 需要读取：
而实际算力消耗约 15 GFLOP（≈ 2 × 参数量），以 4080 的算力零点几毫秒即可完成。
*GPU 绝大部分时间在等数据。 这是 decode 阶段的本质特征，也是所有推理优化的出发点。
批处理能均摊权重，不能均摊 KV
提高并发时，模型权重读一次服务全部请求，可以均摊；但每个请求的 KV 是独立的，
*并发一旦上来，带宽几乎全部被 KV 消耗。 由此逼出两条优化路径：
1. 让 KV 更小 —— MLA、fp8 KV cache、量化（源头治理）
2. 把 KV 挪到别处 —— 分层卸载（本实验台的主题）
2. KV 的存放：PagedAttention 分块
初衷是碎片，共享是副产品
传统做法为每个请求预留一整段连续显存（按最大可能长度），实际用不满即浪费。
PagedAttention 借鉴操作系统的虚拟内存分页，把 KV 切成固定大小的块（vLLM 默认
每块 16 个 token），按需分配、无需连续。
显存利用率因此大幅提升。而「块可以被多个请求共享」是这个设计带来的额外好处，
后来发展成前缀缓存——卸载工作的物理单位也是块。
每块按内容计算哈希（含前序块的哈希链，保证前缀语义）
每个请求持有一张块表，记录逻辑位置 → 物理块的映射
物理块通过引用计数管理生命周期，所有引用者结束后才释放
3. 前缀复用：零拷贝
新请求到达时，逐块比对哈希，命中的块直接被引用，不发生任何数据拷贝。
命中后只是让请求 B 的块表指向同一批物理块：
*没有拷贝、没有搬运、没有额外显存开销，机制类似文件系统的硬链接。
请求 B 的 prefill 从 5050 个 token 降至约 50 个，TTFT 大幅下降。
匹配是逐块进行的哈希链比对，从第一个 token 开始，中间断了则后续全部失效：
工程铁律：共享内容放前面，可变内容放最后。
把用户名、时间戳、会话 ID、随机 ID 放在 prompt 开头是最典型的翻车方式——
看似只差几个 token，实际命中率直接归零。设计压测负载时若忽略这一点，
测出的命中率数据是无效的。
4. 请求生命周期与卸载介入点
*卸载层在 ①②④ 发力，③ 基本不介入。
活跃请求的 KV 必须常驻显存（硬约束）
理论上，由于各层顺序执行，任一时刻只需 1/层数 的 KV 在显存中（Qwen 32K 约 64 MB）。
但这些 KV 每生成一个 token 就要完整过一遍：
慢约 7 倍，交互场景不可接受。即便用逐层预取重叠传输与计算，传输耗时也远大于
各存储层的带宽量级决定了这条约束：以 32K 上下文、1.75 GiB 缓存、30 tokens/s 计算，
持续读取需要约 50 GB/s 带宽。
*因此正在解码的请求，其 KV 只能待在显存里。 卸载的对象是另外两类：
暂时不活跃的请求：并发 50 路但同时只解码 8 路，其余可换出到 CPU，
轮到时换回。换入换出为整块搬运，可与其他请求的计算重叠（vLLM swap_space）。
供未来复用的前缀：只在命中时搬运一次，之后正常常驻参与 decode。
这是 LMCache / HiCache 的主战场。
各层严格顺序执行，因此可在计算第 N 层的同时预取第 N+1 层的 KV：
*用计算时间掩盖传输时间（layer-wise prefetching），LMCache 与 SGLang HiCache
中均有实现。但它的有效范围需要区分清楚：
换言之，分层结构让「搬一次」可以被隐藏，但无法让「每步都搬」变得可行。
L1 最理想但容量有限。卸载方案的价值在于加一层 L2/L3，让装不下的前缀不至于被
直接丢弃——命中时虽需搬运一次，但仍远优于重新计算：
*这就是整个卸载方案的经济账，也是 Phase 3 / Phase 4 要实测的核心数据。

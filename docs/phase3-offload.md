# Phase 3：vLLM 侧 KV 卸载

**日期**：2026-08-02　**硬件**：RTX 4080 16 GiB / WSL2
**版本**：vLLM 0.26.0 + LMCache 0.5.2　**模型**：Qwen2.5-7B-Instruct-AWQ（GQA）

把被 GPU 挤掉的 KV 交给下层存储保管，而不是丢弃重算。本阶段依次验证
CPU 内存 → 本地磁盘 → Redis 三层，量化「搬运」相对「重算」的倍数。

**进度**：CPU 内存层已完成，磁盘与 Redis 层待做。

---

## 1. 实验设计：必须先制造「装不下」

这是本阶段最关键的一步，做不到则所有测量都是平线。

卸载产生收益需要**同时**满足两个条件：

1. 前缀会被**复用**——否则缓存放在哪一层都没有意义
2. 前缀总量**超过 GPU 容量**——否则 GPU 自己就装下了，轮不到下层

原有的两种压测模式都不满足：

| 模式 | 前缀情况 | 问题 |
|---|---|---|
| `--shared` | 全部请求共享同一段 | 只占约 2,900 token，**永远装得下** |
| 默认 | 每请求唯一且不重复 | **从不复用** |

### 新增负载：多会话轮转

`bench_serve.py --sessions N`：N 个会话各有自己的前缀，请求在它们之间轮流。
会话标记置于提示词最开头且不含时间戳——同一会话多次访问前缀完全一致，
不同会话之间从第一块起即不同。

这贴近生产的真实形态：**多个用户的对话历史并存、轮流被访问**。

### 具体规格

| 参数 | 取值 | 依据 |
|---|---|---|
| 单会话前缀 | 2,933 token = 168.2 MB | 由语料决定（57,344 B/token） |
| **GPU KV 上限** | **0.5 GiB = 9,360 token** | `--kv-cache-memory`，约 3.2 个会话 |
| 会话数 | 12（共 35,196 token） | 超配约 3.8 倍，保证轮转一圈必被驱逐 |
| LMCache CPU | 4 GB | 12 × 168 MB = 2 GB，装得下 |
| 并发 | **1** | 见下方说明 |
| 请求数 | 36 | 每会话访问 3 次 |
| 输出长度 | 128 | 见下方说明 |

**并发为什么是 1**：GPU 缓存只有 9,360 token，而单个在途请求就要占约 3,450
（2,933 输入 + 512 预留）。并发 8 需要 27,600 token，远超总容量，vLLM 会陷入
抢占循环——测出来的将是调度噪声而非卸载收益。

**输出为什么只有 128**：本实验测的是**省下的 prefill 成本**，完全体现在 TTFT 上，
生成阶段只会稀释信号。代价是吞吐数字不能与 Phase 2 横向比较。

**`--max-model-len` 必须同步下调**：vLLM 要求 KV 至少装得下一个满长度请求。
32768 需 1.75 GiB，直接拒绝启动并报出所需值。改为 4096。

> 因此**本阶段的绝对数字与 Phase 1/2 基线不可比**，有意义的只有阶段内部的组间对照。
> 启动配置固化在 [`experiments/serve-phase3.sh`](../experiments/serve-phase3.sh)。

## 2. CPU 内存层结果 ✅

原始输出见 [`experiments/results/`](../experiments/results/)。

| | 对照组（无卸载） | LMCache（CPU 层） | 变化 |
|---|---|---|---|
| **TTFT p50** | 439.5 ms | **43.1 ms** | **−90.2%** |
| TTFT p90 | 442.5 ms | 461.4 ms | — |
| TTFT 均值 | 439.7 ms | 181.0 ms | −58.8% |
| ITL p50 | 8.21 ms | 8.20 ms | 无变化 |
| **GPU 前缀缓存命中率** | **0.0%** | **0.0%** | — |
| **外部缓存层命中率** | — | **64.0%** | — |
| 吞吐 | 86.3 tok/s | 103.4 tok/s | +19.8% |
| 总耗时（归一化后） | 53.40 s | 44.09 s | −17.4% |

### 两个交叉验证

**其一：GPU 前缀缓存两组都是 0.0%。** 这是最有力的证据——GPU 缓存一次都没帮上忙，
43 ms 那部分收益**只可能来自 LMCache**，不存在混淆项。

**其二：TTFT 分布是双峰的。**

```
p50 = 43.1 ms      但      p90 = 461.4 ms
```

不是整体变快，而是明确分成两簇：命中约 43 ms、未命中约 460 ms（与对照组的
439 ms 吻合）。按 2/3 命中率加权：

```
1/3 × 460 + 2/3 × 43 = 182 ms  ≈  实测均值 181.0 ms  ✅
```

命中率 64.0% 也符合预期：12 会话各访问 3 次，首次必然未命中，理论上限
`24/36 = 66.7%`。差的 2.7% 是 `chunk_size=256` 对不齐的尾块——LMCache 默认
`save_unfull_chunk: False`，不足一整块的尾巴不入库。

### 换算成带宽

单会话前缀 168.2 MB：

| 路径 | 耗时 | 等效带宽 |
|---|---|---|
| GPU 重新 prefill | 460 ms | **366 MB/s** |
| 从 CPU 内存载回 | 43 ms | **3.9 GB/s** |

**搬运比重算快 10.7 倍。**

那个 366 MB/s 值得单独记住——它是用 Phase 1 基线独立估算过的（约 296 MiB/s），
两次不同方法落在同一量级。**这是 KV 卸载能够成立的定量依据**：任何比它更快的
存储通路，搬都比算划算。

## 3. 方法论：比较总耗时前必须归一化输出长度

对照组输出 4,608 token（`36 × 128`，每个请求都跑满上限），LMCache 组只有 4,283。
少生成的 325 token 本身就省了 `325 × 8.22 ms ≈ 2.67 s`，若直接比较原始耗时会
把降幅高报为 −22.4%。归一化后是 **−17.4%**，恰好对上理论预测：

```
1/3 × (440 + 128×8.2) + 2/3 × (43 + 128×8.2) = 1,224 ms/请求
36 × 1,224 ms = 44.1 s   ≈  归一化后的 44.09 s   ✅
```

**输出长度为什么会不同**：`temperature=0.0` 是贪心解码，但**贪心不等于确定性**。
GPU 浮点归约顺序随批次组成与分块方式变化，KV 是载回的还是重算的也带来末位差异；
而 argmax 是不连续函数，两个 logit 极接近时末位翻转就换词，序列随即分岔。

这属于正常现象，本身不必大惊小怪。真正该记住的是那条方法论：**吞吐按 token 计算
不受影响，但比较墙钟时间前必须归一化输出长度。**

## 4. 收益成立的四个条件

CPU 层跑通只证明了「快」，但真要推广到分布式存储，判据不止带宽一条：

**① 带宽超过重算的等效带宽——且必须按自己的卡重新标定**

366 MB/s 是「4080 + 4-bit 量化模型」的数字。**卡越快，重算越便宜，门槛越高。**
它是个比值而非常数，引用时必须带上硬件与模型。

**② 延迟能被并发摊薄**

上面算的是吞吐，但远程存储还有每次请求的固定延迟。一个会话前缀 168 MB 要取
12 个 chunk（每块 14.7 MiB），若首字节延迟 30 ms：

| 取法 | 延迟 | 传输（按 1 GB/s） | 总计 | vs 重算 460 ms |
|---|---|---|---|---|
| 串行取 12 个 | 360 ms | 168 ms | **528 ms** | **亏** |
| 并行取 12 个 | 30 ms | 168 ms | **198 ms** | 赚 2.3 倍 |

**同样的带宽，串行赔本、并行才赚。** 块大小也因此是个需要调的参数：太小则请求数
暴涨、延迟主导；太大则浪费带宽。

**③ 命中率高到能覆盖写入成本**

本次只测了读。每次未命中除了重算，还要把 KV **写出去**——这笔成本尚未测量。
真实判据是：

```
命中率 × 每次省下的时间  >  (1 − 命中率) × 每次写入的开销
```

**④ 容量足够，且能跨实例共享**

这是分布式存储**不可替代**的地方，且完全不体现在带宽算式里：本地 CPU 内存只服务
本机一个 vLLM 实例；共享存储下，同一用户的请求被负载均衡打到另一台机器上照样命中。
它把命中率从单机视角提升到集群视角——这正是岗位叫「卸载到**分布式**存储」的原因。

## 5. 环境记录

### LMCache 自报的 KV 形状印证了公式

```
kv_shape=(28, 2, 256, 4, 128)
          层  K/V  块  头  维度
28 × 2 × 4 × 128 × 2 字节 = 57,344 字节/token   ← 与 kv_size.py 一致
```

### 依赖变动

`pip install lmcache` 会降级 opentelemetry（1.44.0 → 1.40.0）与 numpy，
但 `pip check` 无冲突，vLLM 0.26.0 功能正常。同时带入 `redis` 客户端，Redis 层可直接用。

### WSL 整体挂死一次

压测过程中 WSL 完全无响应（45 s / 90 s 两次探测均超时），而宿主机内存充足、
CPU 仅 18%——是 WSL 虚拟机自身卡死，只能 `wsl --shutdown` 重启。

根因未确认。可疑点是压测跑在工具调用的**前台**，而那次调用报了内部错误，
可能留下卡住的 wsl 会话让后续调用全部排队。此后改为**后台运行 + 轮询输出文件**，
未再复现。

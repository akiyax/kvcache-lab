# KV Cache 基础原理笔记

日期：2026-08-02

本文记录 KV Cache 的工作原理、各注意力方案的差异，以及这些差异如何决定卸载方案的
设计空间。文中所有数值均由 `experiments/configs/` 中的 `config.json` 快照计算得出。

---

## 1. 为什么会有 KV Cache

注意力机制中，每个 token 都会被投影成三个向量：

| | 名称 | 作用 | 类比 |
|---|---|---|---|
| **Q** | Query | 这个 token 要找什么 | 检索请求 |
| **K** | Key | 这个 token 的可检索标签 | 目录索引 |
| **V** | Value | 这个 token 的实际内容 | 内容本体 |

计算流程：用 Q 与所有 token 的 K 比对得出匹配度（注意力分数），再按匹配度加权汇总
各 token 的 V，得到输出。

以「小明把书放在桌上，因为**它**很重」为例，处理「它」时，它的 Q 表达「我在指代哪个
实体」，与「书」的 K 匹配度最高，于是「书」的 V 被大量吸收进「它」的表示中，模型
由此确定「它 = 书」。

### 为什么只缓存 K 和 V

自回归生成时，第 N 个 token 的 Q 需要与**前面所有 token 的 K** 比对，并汇总它们的 V：

- 前面所有 token 的 K、V → **反复被读取，必须保留**
- 当前 token 自己的 Q → **用完即弃**，后续 token 有各自的 Q

不缓存则每生成一个 token 都要把历史 K、V 全部重算，计算量随长度爆炸。缓存是**以显存
换算力**的交易，代价是显存被 KV 占据，上下文越长占用越多——这正是卸载需求的源头。

---

## 2. 复杂度：存储线性，计算平方

一个常见误解是 KV Cache 占用为 O(N²)。实际上：

| | 复杂度 | 说明 |
|---|---|---|
| 注意力**计算量** | **O(N²)** | 第 i 个 token 要与前 i-1 个比对，累加为平方级 |
| KV Cache **存储量** | **O(N)** | 每个 token 只写入一次 K、V，之后被无限次复用 |

O(N²) 的中间产物是注意力分数矩阵，**计算完即丢弃，不进缓存**。

> 用图论类比：N² 是「边」的数量（token 两两之间的关系），O(N) 是「点」的数量。
> 缓存存的是点，不是边。

---

## 3. 多头注意力与 KV 头数

模型并行运行多组注意力，每组称为一个「头」，各自关注不同的语义侧面。

以 Qwen2.5-7B 为例（`num_attention_heads: 28`、`num_key_value_heads: 4`）：

```
Q1..Q7   Q8..Q14   Q15..Q21   Q22..Q28    ← 28 个 Q 头
   ↓        ↓          ↓          ↓
  KV1      KV2        KV3        KV4      ← 只存 4 组 K/V
```

**`num_key_value_heads` 的含义**：每个 token 在每一层需要存储几组 K/V 向量。
每组包含一个 K 向量和一个 V 向量，维度均为 `head_dim`。

Q 头数不影响缓存（Q 用完即弃），**只有 KV 头数直接决定显存占用**。GQA 的全部价值
就在于压低这个数字。

质量损失有限的原因：各 Q 头的提问角度依然彼此不同，只是共享同一批索引；组内的
若干问题本就语义相近，共用索引损失不大。

## 4. 注意力方案速查

| 缩写 | 全称 | 中文 | KV 头数 | 相对体积 | 代表模型 |
|------|------|------|---------|---------|---------|
| **MHA** | Multi-**H**ead Attention | 多头注意力 | = Q 头数 | 基准 100% | GPT-2、早期 Llama |
| **MQA** | Multi-**Q**uery Attention | 多查询注意力 | 1 | ~3% | PaLM、Falcon |
| **GQA** | **G**rouped-Query Attention | 分组查询注意力 | 中间值 | 12%~25% | Qwen、Llama-3、GLM-4 |
| **MLA** | Multi-head **L**atent Attention | 多头潜在注意力 | 低秩压缩 | 另一套公式 | DeepSeek-V2/V3 |

> 记忆线索看中间的字母：**H**ead（每头一份）→ **Q**uery（全部共享）→
> **G**rouped（分组共享）→ **L**atent（压缩成潜在向量）。

MHA / MQA / GQA 都在调整「保留几组 K/V」这一个维度，MQA 与 MHA 是 GQA 的两个极端。
GQA 是当前的事实标准。

**MLA 不在这条轴上**：它不减少头数，而是把 K、V **联合压缩成一个低秩潜在向量**存储，
使用时再上投影还原。存储量低于 MQA，质量接近 MHA，代价是计算更复杂、对推理框架的
支持要求更高。

### SWA 是另一条正交的轴

**SWA**（**S**liding **W**indow Attention，滑动窗口注意力）常与上面几个并列出现，
但它回答的是完全不同的问题：

```
每个 token 存多少   ──→  MHA / MQA / GQA / MLA    （纵向压缩）
存多少个 token      ──→  全部 / 只保留最近 N 个     （横向截断）
```

**两者正交，可以叠加。** GPT-OSS-20B 即为典型：其 `num_key_value_heads: 8` 是标准
GQA，同时 24 层中有 12 层使用窗口为 128 的滑动窗口。准确描述是「GQA + SWA」，
而非第五种独立方案。（`benchmarks/kv_size.py` 输出中的 `SWA` 标签是简写，
指「含滑窗层的模型」。）

滑窗层只保留最近 N 个 token 的 KV，超出部分直接丢弃，因此其占用不随上下文增长，
在长上下文场景下极为省显存——代价是这些层无法直接看到远处的信息，需依赖全注意力
层与层间传递来弥补，故实践中多为二者交替排列。

## 5. 层数：宽度与深度是两个轴

一个 token 在每一层都是 `hidden_size` 维（Qwen 为 3584），**宽度全程不变**，变的是
数值——每层重新加工一次。

```
         ←──── 宽度：3584 维 ────→
第 1 层   [ 3584 个数字 ]   ↑
第 2 层   [ 3584 个数字 ]   │  深度：28 层
  ...                       │
第 28 层  [ 3584 个数字 ]   ↓
```

- **宽度**（维度）= 每一步能携带多少信息
- **深度**（层数）= 能串联多少步推理

注意力头是把 `hidden_size` **切分**成若干份（28 × 128 = 3584），并非额外增加宽度。

### 为什么需要深度

单层注意力只能完成**一次**信息汇聚。多跳推理必须分层完成，因为后一步的查询依赖
前一步的结果：

```
小明的爸爸是李雷。李雷是医生。问：小明的爸爸做什么工作？

第 N 层  ：小明的爸爸 → 李雷      （结果写入该位置的表示）
第 N+1 层：李雷       → 医生      （基于上一层的结果继续查询）
```

各层存在稳定分工（可解释性研究的普遍结论）：

| 层级 | 主要功能 |
|------|---------|
| 底层 | 词法、局部搭配、基本语法 |
| 中层 | 指代消解、句法结构、语义角色 |
| 高层 | 抽象推理、任务意图、事实调用 |

### 每一层都必须缓存

生成下一个 token 需要**从第 1 层重新走完整前向传播**，每层的注意力都要查询**该层
自己的**缓存。注意力不跨层，层间只通过「输出→输入」传递。

因此 28 层就是 28 套互相独立、不可替代的缓存：

> KV Cache 存的不是「一份数据的 28 个副本」，而是「28 个不同抽象层次的理解快照」。

### 与「思考深度」无关

推理模型的 thinking budget / reasoning effort 是**横向**延长序列（生成更多思考
token），与**纵向**的层数无关。层数在训练时定死，推理时无法调整。

但思考模式会显著放大 KV 占用——思考 token 与普通 token 在注意力机制中毫无区别，
全部正常写入缓存：

| 场景 | token 数 | KV 占用（按 Qwen 56 KiB/token） |
|------|---------|---------------------------------|
| 普通问答 | ~500 | 27 MiB |
| 开启思考 | ~8500 | 465 MiB |

**思考内容能否跨请求复用前缀，取决于它是否保留在对话历史中**，两种情况都很常见：

- **被剥离 → 不可复用**：DeepSeek-R1、Qwen3 等模型的官方建议是多轮对话时不要把
  上一轮的 `reasoning_content` 放回历史（对后续轮次无价值，且浪费上下文窗口）。
  此时思考 token 生成后即废弃，进不了可复用前缀。
- **被保留 → 高度可复用**：Agent 的工具调用循环中，每次工具调用都是独立请求，
  而上下文（含此前的思考内容）持续累积。这是前缀缓存收益最大的场景之一。

**对卸载而言，思考模式的主要压力在生成期间的活跃显存占用，而非缓存复用。**
单个开启思考的请求在生成过程中需持续持有数百 MiB 的 KV 且只增不减，并发几路即可
占满显存。这与长文档场景的「一次性 prefill 大量 KV、之后大量复用」是两种不同的
负载模式，卸载策略也应有所区别——前者需要的是活跃请求的换入换出，后者需要的是
高命中率的前缀池。

## 6. KV 体积计算公式

### GQA

```
单 token = 层数 × 2 × KV头数 × head_dim × 每元素字节数
                   ↑ K 和 V 各一份
```

### MLA

```
单 token = 层数 × (kv_lora_rank + qk_rope_head_dim) × 每元素字节数
```

- **无 ×2**：K 与 V 被联合压缩进同一个潜在向量，一份数据同时还原 K 和 V
- **无 ×头数**：该潜在向量为所有头共享
- **+ qk_rope_head_dim**：RoPE 无法作用于压缩表示，故位置编码部分（解耦 RoPE）
  单独保留，同样全头共享

### 滑动窗口

```
单 token = 全注意力层数 × 2 × KV头数 × head_dim × 字节数    （随上下文线性增长）
常数项   = 滑窗层数 × 2 × KV头数 × head_dim × 字节数 × 窗口大小   （封顶）
```

### 关于精度

`quantization_config` 描述的是**权重量化，与 KV 精度无关**。AWQ 4-bit 模型的 KV
默认仍是 fp16/bf16（2 字节）。vLLM 可通过 `--kv-cache-dtype fp8` 将 KV 减半，
这是 Phase 3 的实验变量之一。

## 7. 实测数据

上下文 32K、单序列、KV 精度 2 字节：

| 模型 | 方案 | 每层存储量 | 层数 | 单 token | @32K |
|------|------|-----------|------|---------|------|
| GLM-4-9B-Chat | GQA(2) | 2×2×128 = 512 | 40 | 40.0 KiB | 1.25 GiB |
| DeepSeek-V2-Lite | MLA | 512+64 = 576 | 27 | 30.4 KiB | 0.95 GiB |
| Qwen2.5-7B-AWQ | GQA(4) | 4×2×128 = 1,024 | 28 | 56.0 KiB | 1.75 GiB |
| Llama-3.1-8B-AWQ | GQA(8) | 8×2×128 = 2,048 | 32 | 128.0 KiB | 4.00 GiB |
| GPT-OSS-20B | 滑窗(128) | 8×2×64 = 1,024 | 12 全 + 12 滑 | 24.0 KiB † | 0.75 GiB |

† GPT-OSS 为两段式：12 层全注意力线性增长，12 层滑窗在 128 token 处封顶（3 MiB 常数）。

**「每层存储量 × 层数」是理解差异的正确视角**：GLM 层数比 Qwen 多（40 vs 28），但
每层只有一半的 KV 头，净结果仍更省。

作为对照，若 Qwen 退回 MHA（28 组 KV），单 token 将达 **392 KiB**，是 GQA 方案的 7 倍。

## 8. config.json 字段与陷阱

五份配置使用了**四套互不兼容的命名体系**：

| 架构 | `model_type` | 关键字段 |
|------|--------------|---------|
| GQA（标准） | `qwen2` / `llama` | `num_hidden_layers`、`num_key_value_heads`、`hidden_size` |
| GQA（ChatGLM） | `chatglm` | `num_layers`、`multi_query_group_num`、`kv_channels` |
| MLA | `deepseek_v2` | `num_hidden_layers`、`kv_lora_rank`、`qk_rope_head_dim` |
| 滑动窗口 | `gpt_oss` | `layer_types`、`sliding_window`、`head_dim` |

已确认的陷阱：

| # | 陷阱 | 出现在 | 后果 |
|---|------|--------|------|
| 1 | `head_dim` 缺失，需由 `hidden_size / num_attention_heads` 推导 | Qwen、Llama、GLM | 需 fallback 逻辑 |
| 2 | `head_dim` 显式存在且 **≠** 推导值（64 vs 2880/64=45） | **GPT-OSS** | 盲目推导**低估 42%** |
| 3 | `num_key_value_heads: 16` 为残留字段，MLA 不使用 | **DeepSeek** | 误用 GQA 公式**高估 8.9 倍** |
| 4 | `sliding_window: 131072` 但 `use_sliding_window: false` | **Qwen** | 误走滑窗公式 |
| 5 | 整套字段名不同，标准 key 不存在 | **GLM** | 直接 `KeyError` |
| 6 | 无 `torch_dtype` 字段 | **GPT-OSS** | 字节数无从判断，需默认值 |
| 7 | `use_cache: false` | Llama AWQ | 不影响 KV 计算，起服务时留意 |

**结论：KV 体积计算必须先读 `model_type` 分派公式，`head_dim` 优先取显式值，
滑窗需检查开关，缺失必需字段应明确报错而非静默使用默认值。**

## 9. 对卸载工作的意义

### 带宽墙

每生成一个 token，**整个 KV Cache 都要被完整读取一次**。以 32K 上下文、1.75 GiB
缓存、30 tokens/s 计算，需要约 **50 GB/s** 的读带宽：

| 存储层 | 量级带宽 | 是否可行 |
|--------|---------|---------|
| GPU 显存 | ~700 GB/s | 充裕 |
| 主机内存（PCIe 4.0 x16） | ~25 GB/s | 吃紧 |
| NVMe SSD | ~5 GB/s | 不可行 |
| 网络（100Gb） | ~12 GB/s | 不可行 |

**所以卸载的难点不在「搬出去」，而在「及时读回来」。** 可行方案依赖：只卸载非活跃
请求、按需分块预取、前缀复用（命中则无需重算也无需搬运）等策略。

### 分层结构带来的流水线机会

由于各层**严格顺序执行**，可在计算第 N 层的同时预取第 N+1 层的 KV：

```
GPU 计算第 5 层  ┐
                 ├─ 并行 ─→  从 CPU / 远端预取第 6 层 KV
                 ┘
```

**用计算时间掩盖传输时间**（layer-wise prefetching），是 KV 卸载能够落地的关键技巧，
LMCache 与 SGLang HiCache 中均有实现。若 KV 是不可分割的整体，传输延迟将完全暴露。

### 方案选择的影响

单 token KV 体积直接决定卸载的可行性——同样的存储后端带宽，MLA 方案（30.4 KiB）
比 Llama 的 GQA（128 KiB）宽裕 4.2 倍。这也是 MLA 对分布式 KV 存储场景格外重要的
原因，以及本实验台把 DeepSeek-V2-Lite 列为主线模型的理由。

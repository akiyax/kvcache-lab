# 推理系统侧的 KV Cache 管理

前三篇讲的是**模型架构决定 KV 有多大**，本文讲**推理系统如何存放、复用和搬运这些
KV**——也就是卸载工作的实际战场。

文中带具体数字的推算均标注了假设条件，未经实测的部分列在文末「待验证」中。

---

## 1. Prefill 与 Decode：两种截然不同的负载

同一套权重、同一套代码，但数据形状差异巨大，导致两个阶段的瓶颈完全不同。

| | **Prefill**（处理输入） | **Decode**（逐 token 输出） |
|---|---|---|
| 一次处理 | 全部 N 个 token | **1 个 token** |
| Q 的形状 | N × hidden_size | **1 × hidden_size** |
| KV 操作 | 边算边填入缓存 | 追加 1 个，**读取全部历史** |
| 矩阵乘法 | 大矩阵 × 大矩阵 | 向量 × 大矩阵 |
| 瓶颈 | **算力** | **显存带宽** |
| 对应指标 | TTFT | 吞吐（tokens/s） |

### Decode 的单步流程

```
上一个 token 的 embedding  [hidden_size]
         ↓
┌─ 每一层 ─────────────────────────────────────┐
│  x @ W_Q  →  Q   ← 用完即弃                  │
│  x @ W_K  →  K   ← 追加进本层缓存            │
│  x @ W_V  →  V   ← 追加进本层缓存            │
│                                              │
│  注意力：各 Q 头扫过本层缓存的全部 N+1 个位置 │
│  → 输出投影 → FFN                            │
└──────────────────↓───────────────────────────┘
        ... 重复所有层 ...
                   ↓
              lm_head → 采样 → 下一个 token → 回到顶部
```

### Decode 是带宽瓶颈

以 Qwen2.5-7B-AWQ、32K 上下文、RTX 4080 估算，生成**一个** token 需要读取：

```
模型权重      ~5.5 GB    （所有层的 W_Q/W_K/W_V/FFN 都要过一遍）
KV 缓存       ~1.75 GB   （32K × 56 KiB）
             ──────────
             ~7.25 GB    ÷ ~716 GB/s ≈ 10 ms  →  约 100 tokens/s
```

而实际算力消耗约 15 GFLOP（≈ 2 × 参数量），以 4080 的算力**零点几毫秒即可完成**。

```
搬数据：~10 ms    ████████████████████
做计算：~0.3 ms   █
```

**GPU 绝大部分时间在等数据。** 这是 decode 阶段的本质特征，也是所有推理优化的出发点。

### 批处理能均摊权重，不能均摊 KV

提高并发时，模型权重**读一次服务全部请求**，可以均摊；但每个请求的 KV 是独立的，
**完全无法均摊**：

| 并发数 | 权重读取（均摊后） | KV 读取 | KV 占比 |
|--------|------------------|---------|---------|
| 1 | 5.5 GB | 1.75 GB | 24% |
| 8 | 0.69 GB | 14 GB | 95% |
| 32 | 0.17 GB | 56 GB | **99.7%** |

**并发一旦上来，带宽几乎全部被 KV 消耗。** 由此逼出两条优化路径：

1. **让 KV 更小** —— MLA、fp8 KV cache、量化（源头治理）
2. **把 KV 挪到别处** —— 分层卸载（本实验台的主题）

## 2. KV 的存放：PagedAttention 分块

### 初衷是碎片，共享是副产品

传统做法为每个请求预留一整段**连续显存**（按最大可能长度），实际用不满即浪费。
PagedAttention 借鉴操作系统的虚拟内存分页，把 KV 切成**固定大小的块**（vLLM 默认
每块 16 个 token），按需分配、无需连续。

显存利用率因此大幅提升。而「**块可以被多个请求共享**」是这个设计带来的额外好处，
后来发展成前缀缓存——**卸载工作的物理单位也是块**。

### 块的管理

- 每块按内容计算哈希（含前序块的哈希链，保证前缀语义）
- 每个请求持有一张**块表**，记录逻辑位置 → 物理块的映射
- 物理块通过**引用计数**管理生命周期，所有引用者结束后才释放

---

## 3. 前缀复用：零拷贝

新请求到达时，逐块比对哈希，命中的块**直接被引用，不发生任何数据拷贝**。

```
请求 A：[系统提示 2000] + [文档 3000] + [问题甲 50]
        └─────── 算出 KV，存为约 316 个块 ───────┘

请求 B：[系统提示 2000] + [文档 3000] + [问题乙 50]
        └──── 哈希一致，命中约 312 块 ────┘  └ 仅需计算约 4 块 ┘
```

命中后只是让请求 B 的块表指向同一批物理块：

```
请求 A 的块表 ──┐
                ├──→ [块1][块2]...[块312]   ← 物理块只有一份
请求 B 的块表 ──┘
```

**没有拷贝、没有搬运、没有额外显存开销**，机制类似文件系统的硬链接。
请求 B 的 prefill 从 5050 个 token 降至约 50 个，TTFT 大幅下降。

### 必须从头连续匹配

匹配是逐块进行的哈希链比对，**从第一个 token 开始，中间断了则后续全部失效**：

```
✅  [系统提示][文档][问题甲]
    [系统提示][文档][问题乙]      → 前面全部命中

❌  [时间戳][系统提示][文档]
    [时间戳'][系统提示][文档]     → 第一块即不同 → 后续全部失效
```

> **工程铁律：共享内容放前面，可变内容放最后。**
>
> 把用户名、时间戳、会话 ID、随机 ID 放在 prompt 开头是最典型的翻车方式——
> 看似只差几个 token，实际命中率直接归零。设计压测负载时若忽略这一点，
> 测出的命中率数据是无效的。

## 4. 请求生命周期与卸载介入点

```
请求到达
   ↓
① 查前缀缓存  →  命中则把 KV 从 CPU/远端搬回显存        ★ 卸载层发力
   ↓               （省去重新 prefill，TTFT 显著下降）
② Prefill 未命中部分  →  新算出的 KV 可同时写一份到卸载层  ★ 卸载层发力
   ↓
③ Decode 逐 token 生成  →  KV 常驻显存，原地读取，不搬运   ☆ 卸载层不介入
   ↓                        （仅在显存不足被抢占时 swap out）
④ 请求结束  →  KV 留在缓存池等待未来命中                  ★ 卸载层发力
```

**卸载层在 ①②④ 发力，③ 基本不介入。**

### 活跃请求的 KV 必须常驻显存（硬约束）

理论上，由于各层顺序执行，任一时刻只需 1/层数 的 KV 在显存中（Qwen 32K 约 64 MB）。
但这些 KV **每生成一个 token 就要完整过一遍**：

| 方案 | 每 token 传输量 | 估算耗时 | 速度 |
|------|---------------|---------|------|
| 全部常驻显存 | 0（原地读取） | ~10 ms | ~100 tok/s |
| 逐层从 CPU 取 | 1.75 GB 过 PCIe 4.0 | ~70 ms | **~14 tok/s** |

慢约 7 倍，交互场景不可接受。即便用逐层预取重叠传输与计算，传输耗时也远大于
计算耗时，无法藏住。

各存储层的带宽量级决定了这条约束：以 32K 上下文、1.75 GiB 缓存、30 tokens/s 计算，
持续读取需要约 **50 GB/s** 带宽。

| 存储层 | 量级带宽 | 能否支撑 decode 期间的持续读取 |
|--------|---------|------------------------------|
| GPU 显存 | ~700 GB/s | 充裕 |
| 主机内存（PCIe 4.0 x16） | ~25 GB/s | 吃紧 |
| NVMe SSD | ~5 GB/s | 不可行 |
| 网络（100Gb） | ~12 GB/s | 不可行 |

**因此正在解码的请求，其 KV 只能待在显存里。** 卸载的对象是另外两类：

- **暂时不活跃的请求**：并发 50 路但同时只解码 8 路，其余可换出到 CPU，
  轮到时换回。换入换出为整块搬运，可与其他请求的计算重叠（vLLM `swap_space`）。
- **供未来复用的前缀**：只在命中时搬运一次，之后正常常驻参与 decode。
  这是 LMCache / HiCache 的主战场。

### 逐层预取的适用边界

各层严格顺序执行，因此可在计算第 N 层的同时预取第 N+1 层的 KV：

```
GPU 计算第 5 层  ┐
                 ├─ 并行 ─→  从 CPU / 远端预取第 6 层 KV
                 ┘
```

**用计算时间掩盖传输时间**（layer-wise prefetching），LMCache 与 SGLang HiCache
中均有实现。但它的有效范围需要区分清楚：

| 场景 | 是否有效 | 原因 |
|------|---------|------|
| 前缀命中后**一次性搬入** | ✅ 有效 | 搬运只发生一次，可与首次前向计算重叠 |
| 换出请求的**整块换回** | ✅ 有效 | 可与其他请求的计算重叠 |
| decode 期间**每 token 流式喂养** | ❌ 无效 | 每 token 需搬 1.75 GiB 而计算仅 10 ms，藏不下 |

换言之，分层结构让「搬一次」可以被隐藏，但无法让「每步都搬」变得可行。

## 5. 分层与经济账

| 层次 | 位置 | 命中时的操作 | 开销 |
|------|------|------------|------|
| **L1** | 本卡显存 | 块表指过去 | **零拷贝** |
| **L2 / L3** | CPU 内存 / 磁盘 / Redis / 对象存储 | 搬回显存 | 一次传输 |
| **集群路由** | 其他实例 | 把请求路由过去 | 网络跳转 |

L1 最理想但容量有限。卸载方案的价值在于**加一层 L2/L3，让装不下的前缀不至于被
直接丢弃**——命中时虽需搬运一次，但仍远优于重新计算：

```
重新 prefill 5000 token   →  几百 ms（受算力限制）
从 CPU 搬 KV 回显存        →  几十 ms（受带宽限制）
```

**这就是整个卸载方案的经济账**，也是 Phase 3 / Phase 4 要实测的核心数据。

### 集群层：cache-aware routing

多实例部署时，若请求随机分发，前缀缓存基本失效：

```
              ┌── 实例 1（已缓存客户 A 的文档）
   路由器 ────┤
              └── 实例 2（已缓存客户 B 的文档）

   客户 A 的新请求 → 路由器识别前缀 → 定向派给实例 1
```

SGLang 的负载均衡器与 vLLM 的 router 均实现了这类前缀感知路由。本实验台为单卡，
该层暂不涉及，但它是生产环境的标配。

### 与负载类型的关系

不同负载对卸载层的需求不同，应分别测量：

| | 长文档问答 | 思考 / Agent 循环 |
|---|---|---|
| KV 特征 | 一次性 prefill 大量，之后大量复用 | 缓慢持续增长，当前请求必须常驻 |
| 前缀命中率 | 高（共享文档前缀） | 取决于思考内容是否保留在历史中 |
| 卸载需求 | 高命中率的**前缀池** | 活跃请求的**换入换出** |
